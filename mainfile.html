Overview of Software Engineering

What software is, how a process is organised, the classic and evolutionary process models, Agile and XP, and where system engineering fits. The FAT tests this by giving you a project and asking which model fits.

Asked in all 3 papers~20 marks per paper

Software and software engineering

Software (Pressman) is three things together: (1) instructions that deliver features and performance, (2) data structures that let those programs handle information, and (3) documentation describing how to operate and use them. A program is just the code; software = program + documentation + operating procedures.

Software engineering is the systematic, disciplined, measurable approach to developing, operating and maintaining software. In short: applying engineering to software so it ships on time, on budget, and works.

Why software is different from hardware

  • It is engineered, not manufactured. Cost is in design and development, not in making copies.
  • It doesn't wear out, it deteriorates. No physical decay, but every change risks new defects, so the failure curve gets spikier over time.
  • Most of it is still custom built, even though component reuse is growing.

Application domains

System software (compilers, OS, drivers) · Application software (business apps) · Engineering/scientific · Embedded (ABS, microwave) · Product-line · Web & mobile apps · AI software. Legacy software is old software that still runs the business: costly to maintain, risky to change, often poorly documented.

Software crisis

The 1960s–70s realisation that projects were routinely late, over budget, unreliable and hard to maintain. Software engineering exists as the response.

Exam tip“Need for software engineering” answers: handles large/complex systems, reduces cost, cuts time, makes software reliable and maintainable, manages change and quality. Five points is plenty.

Classical (plan-driven) models FAT favourite

Waterfall

1 · Requirements analysis & SRS2 · System & software design3 · Implementation & unit testing4 · Integration & system testing5 · Deployment6 · Maintenance
Use whenRequirements are stable and well understood, technology is known, the project is short, heavy documentation is required (regulated domains).
Weak atLate changes are expensive; working software appears only at the end; testing is late so defects are found late; poor for long or uncertain projects.

V-model (Verification & Validation model)

Waterfall bent into a V. Every development phase on the left has a matching test phase on the right, and the test plans are written during the left-side phase. Left side = verification (static: reviews, “are we building it right?”). Right side = validation (dynamic: execution, “are we building the right thing?”).

Use whenSafety-critical or regulated systems (medical, avionics, automotive), stable requirements, traceability from requirement to test is mandatory.
Weak atRigid; no early prototypes; changes mid-way force updates to both sides of the V.
Exam tip“Classical models” = Waterfall and V-model (linear, sequential). “Evolutionary models” = Prototyping, Spiral, Incremental/Iterative, Concurrent. The syllabus pairs them, so you may be asked to combine one of each (see the MediCare hybrid question).

Evolutionary and incremental models

These models accept that requirements change. Software grows through versions, each one more complete than the last.

Incremental model

Split the system into increments. Each increment goes through requirements → design → code → test and is delivered. Increment 1 is the core product; later increments add features.

Increment 1 (core)AnalysisDesignCodeTestDeliver v1
Increment 2AnalysisDesignCodeTestDeliver v2
Increment nAnalysisDesignCodeTestDeliver vn

Use when the core requirements are clear but extras can come later, an early release is needed, or the product must ship in phases. Watch out for: needs good upfront architecture so increments fit together.

Iterative model

Start with a simple version of the whole system, then refine it over repeated cycles (plan → design → implement → test → review). Incremental adds new pieces; iterative improves the same pieces. Most real projects mix both.

Prototype model

Build a quick, rough version so users can react to it, then refine requirements. Steps: requirements gathering → quick design → build prototype → user evaluation → refine (loop) → engineer the real product.

Use when requirements (especially UI) are unclear. Risk: the customer mistakes the prototype for the product; throwaway code sneaks into production.

Spiral model (Boehm)

A risk-driven model. Each loop of the spiral is one phase, and every loop passes through four quadrants. The radius shows cumulative cost; the angle shows progress.

Use whenLarge, expensive, high-risk projects; requirements are complex or partly unknown; long timeline with releases; frequent risk evaluation is needed.
Weak atCostly; needs risk-assessment expertise; overkill for small, low-risk projects; hard to say when it ends.

RAD (Rapid Application Development)

Very short cycle (60–90 days) using component reuse, CASE tools and several teams working in parallel on separate modules.

Business modellingData modellingProcess modellingApplication generationTesting & turnover

Use when the system can be modularised and delivered in a short span (2–3 months), requirements are well known, technical risk is low, and skilled developers with RAD tools are available. Weak at: large systems that can't be split, high technical risk, teams without the skill.

Big Bang model

No planning, all effort into coding, integrate everything at the end. Only for tiny, academic or experimental projects.

Agility and the Agile process

Agility means responding to change quickly. Agile development delivers working software in short iterations (1–4 weeks) with the customer involved throughout.

The 12 principles, condensed

  1. Satisfy the customer through early, continuous delivery.
  2. Welcome changing requirements, even late.
  3. Deliver working software frequently (weeks, not months).
  4. Business people and developers work together daily.
  5. Build around motivated individuals; trust them.
  6. Face-to-face conversation is the best communication.
  7. Working software is the main measure of progress.
  8. Sustainable pace, indefinitely.
  9. Continuous attention to technical excellence and good design.
  10. Simplicity: maximise the work not done.
  11. Best designs emerge from self-organising teams.
  12. Reflect regularly and adjust (retrospectives).

Overview of system engineering

A system is more than software: hardware, software, people, procedures, data and documentation working together. System engineering looks at the whole and decides which part does what before software engineering starts on the software part.

Principles of system engineering

  • Holistic (system) view: optimise the whole system, not one component.
  • Requirements definition and allocation: system requirements are split and allocated to hardware, software, people and civil/mechanical parts.
  • Interface management: define how subsystems talk (interface control documents).
  • Trade-off analysis: decide what goes in hardware vs software based on cost, performance, risk.
  • Integration and system-level V&V: subsystems are integrated and tested as a whole.
  • Life-cycle thinking: includes operation, maintenance and decommissioning.

System engineering vs software engineering

System engineering is the umbrella. It produces the system specification and architecture, then hands the software part to software engineering, which builds it using a process model. The two keep talking because hardware changes affect software and vice versa.

System software (as in your slides)

Programs that manage hardware and provide a platform for applications (OS, compilers, drivers). Objectives: manage resources, provide a platform, improve performance, ensure security, connect hardware and software. Layers: Hardware → System software → Application software.

Project planning and scope

Planning starts before any technical work. It answers: what will we build, how long, how much, who, and what could go wrong.

Planning activities

Define scopeFeasibilityEffort estimationCost estimationResource planningSchedulingRisk planningQuality planningCommunication & SCM planning

Scope states what is in and out of the project: functions, performance, constraints, interfaces, reliability. Scope creep (uncontrolled additions) is a top cause of failure.

Feasibility: technical, economic, operational, schedule, legal.

Resources: human (PM, analyst, developers, testers, UI/UX, DBA), hardware (servers, devices), software (IDE, DB, VCS, testing tools).

WBS, milestones and deliverables Apr 25 Q3

A Work Breakdown Structure breaks the total work into smaller, manageable pieces in a hierarchy. The lowest level is a work package, small enough to estimate, assign and track. The 100% rule: the children add up to exactly the parent's work, nothing more or less.

Deliverable-based WBSDecompose by outputs: Website → Front end, Back end, Database, Documentation.
Phase-based WBSDecompose by life-cycle phase: Requirements, Design, Development, Testing, Deployment.

How to build one: identify the final deliverable → decompose into major deliverables/phases → decompose into work packages → assign owners and estimates → review with the team.

Brooks' law E2 Q3

“Adding manpower to a late software project makes it later.” (Fred Brooks, The Mythical Man-Month, 1975). Three reasons:

  • Ramp-up time: new people need weeks to learn the code and domain, and existing members spend time training them.
  • Communication overhead: channels grow as n(n−1)/2. 8 people = 28 channels; 16 people = 120.
  • Limited divisibility: some tasks can't be split (nine women can't make a baby in one month).

Alternatives: cut or defer scope, re-plan milestones, add a few specialists early (not many late), remove blockers, automate testing and builds.

Risk management and RMMM E1 Q2

A risk is a problem that hasn't happened yet but could cause loss. Two properties: uncertainty (probability) and loss (impact).

By what it threatensProject risks: schedule, budget, staff, customer.
Technical risks: design, implementation, interfaces, ambiguous or changing specs, obsolete tech.
Business risks: building something nobody wants, losing budget or management support.
By how visibleKnown: found by careful evaluation (unrealistic deadline).
Predictable: from past projects (staff turnover).
Unpredictable: can happen but hard to foresee.

Principles

Global perspective · Forward-looking view · Open communication · Integrated management · Continuous process.

Risk management activities

  • Identification: brainstorming, checklists, past projects, assumption analysis.
  • Analysis: estimate probability and impact. Risk Exposure RE = P × C (C = cost if it happens).
  • Prioritisation: sort by RE in a risk table; cut-off line for what gets managed.
  • Strategies: avoid, transfer (insurance, outsourcing), reduce/mitigate, accept.
  • Risk leverage = (RE before − RE after) / cost of reduction. Pick actions with high leverage.
  • Monitoring: watch triggers, update the risk register each sprint/week.

RMMM plan = Mitigation, Monitoring, Management

MitigationProactive steps to reduce probability or impact before it happens (cross-training, backups).
MonitoringTrack indicators that the risk is becoming real (attendance, morale, velocity).
ManagementContingency plan for when it does happen (reassign work, use buffer).

SRS and its characteristics

The Software Requirements Specification describes what the software will do (not how). Readers: customers, managers, developers, testers.

Characteristics of a good SRS (IEEE 830)

Data Flow Diagrams Apr 25 Q10b, E1 Q4a

A DFD shows how data moves through a system: where it comes from, what transforms it, where it's stored, where it goes. It shows no control flow, loops or timing.

Levels

  • Level 0 / Context diagram: the whole system as one process, with all external entities and the main flows. No data stores.
  • Level 1: the single bubble exploded into 5–7 major processes (1.0, 2.0…), with data stores.
  • Level 2: one Level-1 process exploded further (2.1, 2.2…).

Rules that examiners check

  • Balancing: inputs/outputs of a parent bubble must equal those of its child diagram.
  • Every process has at least one input and one output.
  • Data can't flow directly entity → entity, store → store, or entity → store. A process must sit in between.
  • Label every flow with a noun (the data), every process with a verb phrase.
  • Keep 5–9 processes per diagram; duplicate an entity or store (mark with a slash) rather than draw long crossing lines.

Transform and transaction mapping

Both turn a DFD into a program structure chart (a call hierarchy of modules).

Transform flowData comes in (incoming/afferent flow), gets transformed in the middle (transform centre), and goes out (outgoing/efferent flow). A steady, linear pipeline.
Transaction flowOne input (a transaction) arrives at a transaction centre that dispatches it to one of several action paths.

Transform mapping steps

  1. Review the system model; refine the DFD.
  2. Decide the DFD has transform characteristics.
  3. Isolate the transform centre by marking the incoming and outgoing flow boundaries.
  4. First-level factoring: a main controller with three children: input controller, transform controller, output controller.
  5. Second-level factoring: map each bubble to a module under its controller.
  6. Refine using cohesion and coupling heuristics.

Transaction mapping steps

  1. Review and refine the DFD.
  2. Identify the transaction centre and the flow characteristics of each action path.
  3. Map the DFD to a structure: a transaction controller with a dispatcher and one sub-controller per action path.
  4. Factor and refine each action path (each may be transform flow internally).

Refactoring of designs

Refactoring changes the internal structure of code or design without changing its external behaviour, to make it cleaner and easier to maintain.

  • Purpose: remove duplication, simplify complex logic, improve names and structure, reduce coupling, raise cohesion, pay down technical debt.
  • Techniques: extract method/class, rename, move method, replace conditional with polymorphism, introduce parameter object, remove dead code.
  • Benefits: readability, maintainability, fewer bugs, easier extension, better performance sometimes.
  • Challenges: time cost, risk of breaking behaviour, needs good tests, hard to justify to management.
  • Best practices: small steps, test before and after, refactor with the team, use tools (IDE refactorings, SonarQube), refactor before adding features, don't mix with feature changes.

White-box testing and cyclomatic complexity numerical: Apr 25 Q9a, E1 Q5

Test the internal logic. Coverage levels: statement (every line once) < branch/decision (every true and false outcome) < path. Basis path testing (McCabe) gives the minimum set of independent paths that covers every branch.

Steps

  1. Number the statements; draw the control flow graph (nodes = statements/blocks, edges = flow of control; each decision node has two exits).
  2. Compute cyclomatic complexity V(G).
  3. List V(G) linearly independent paths (each adds at least one new edge).
  4. Design a test case (input + expected output) to force each path.
V(G) = E − N + 2 (edges − nodes + 2) V(G) = P + 1 (P = predicate/decision nodes) V(G) = number of regions (enclosed areas + outer region) Compound condition (a && b) counts as 2 predicates.

Mutation testing

Tests the tests. Make small deliberate changes (mutants) to the program and run the test suite. If a test fails, the mutant is killed (good). If all pass, it survived and the suite is weak.

  • Value mutation: change constants (x = 10 → x = 11).
  • Decision mutation: change operators (> → >=, && → ||).
  • Statement mutation: delete, duplicate or swap statements.
Mutation score = killed mutants / (total mutants − equivalent mutants) × 100%

Steps: write tests → create mutants → run tests on original and mutants → compare outputs → add tests to kill survivors. Tools: PIT (Java), MutPy, Stryker.

Object-oriented testing E2 Q7

In OO software the unit is the class, not a function. Inheritance, polymorphism and encapsulation create new kinds of faults: a method that works in the parent may fail in a child; a call may bind to an unexpected subclass; state hidden inside objects affects behaviour.

  • Class testing (OO unit testing): test each operation and sequences of operations on one class, including its state.
  • State-based testing: derive tests from the class's state diagram; cover every state and every transition, including illegal events.
  • Inheritance testing: retest inherited methods in the context of each subclass; overridden methods need new tests.
  • Polymorphism testing: test each possible binding of a polymorphic call (every subclass a caller might receive).
  • Integration testing: thread-based (classes needed for one input/event), use-based (independent classes first, then dependent layers), cluster testing (a group of collaborating classes).
  • Validation: use-case/scenario-based tests; fault-based tests targeting plausible faults.

Software Configuration Management every paper

SCM is the discipline of identifying, controlling, tracking and auditing changes to software throughout its life. Many people produce many work products (code, docs, test data); SCM keeps them consistent.

  • Software Configuration Item (SCI): any controlled item: SRS, design, source file, test plan, build script.
  • Baseline: a formally reviewed and agreed version of SCIs; it changes only through formal change control. (“SRS v1.0 approved” is a baseline.)
  • Version vs release: a version is any instance; a release is a version distributed to customers.

Access control decides who may check out an object; synchronisation control stops two people overwriting each other's changes (locking or merging).

SCM vs version control: version control is one part of SCM (tracking file versions). SCM also covers identification, change control, audits, status accounting and releases.

Re-engineering, reverse engineering, refactoring

Software re-engineering = examining and altering an existing (legacy) system to rebuild it in a new form, usually to improve maintainability or move to new technology, while keeping its functionality.

Re-engineering process

Inventory analysisDocument restructuringReverse engineeringCode restructuringData restructuringForward engineering

Simply put: Re-engineering = Reverse engineering + Restructuring + Forward engineering.

  • Objectives: lower maintenance cost, migrate platform, improve quality and documentation, extend life of a valuable system.
  • Cost factors: quality of the existing software, tool support, extent of data conversion, availability of expert staff.
  • Advantages: cheaper and less risky than full replacement (functionality is known), reuses business knowledge.
  • Disadvantages: practical limits on how much can be improved; still costly; may not fix fundamental architecture problems.

Reverse engineering

Analysing a system to extract design and specification information from its code: going from low abstraction to high. Steps: collect information → examine it → extract structure → record functionality → record data flow → record control flow → review the recovered design → generate documentation. Tools: IDA Pro, Ghidra (binaries), Doxygen, Enterprise Architect, Visual Paradigm (code → UML).

ISO standards

The ISO 9000 family is a generic quality-management standard: it certifies that an organisation has a documented quality system and follows it. It does not certify the product itself.

  • ISO 9001: design, development, production, installation and servicing. Applies to software development organisations.
  • ISO 9002: production, installation, servicing (no design). ISO 9003: final inspection and testing only.
  • ISO 9000-3: guidelines for applying ISO 9001 to software.
  • Related: ISO/IEC 12207 (software life-cycle processes), ISO/IEC 25010 (product quality), ISO/IEC 15504 SPICE (process assessment).

Certification steps: application → pre-assessment → document review → on-site audit and corrective actions → registration → continued surveillance audits.

ISO vs CMM: ISO certifies an organisation (pass/fail), is generic for any industry; CMM is software-specific and has five graded levels focused on continuous improvement.
